## 2024-06-27 - Information Exposure via Database Errors
**Vulnerability:** The application was catching raw database errors from Supabase during form submissions and displaying the `err.message` directly in the UI via `setError()`, potentially leaking internal database schema details or stack traces to malicious users. Furthermore, it lacked client/server-side input validation on maximum lengths, making it susceptible to minor DoS attacks or saving malformed data.
**Learning:** Even in serverless/direct-to-database architectures like Supabase, error messages originating from the database layer must be sanitized or mapped to generic safe responses before being exposed to the client. We cannot trust the database error object to be UI-safe.
**Prevention:** Always implement an allowlist for known, safe validation errors (e.g., custom format or length errors generated by our own code) and use a generic fallback message for any other exceptions. Add strict bounds checking (e.g., length and regex format) on all user-provided data before attempting database operations.
